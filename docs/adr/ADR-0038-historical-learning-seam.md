# ADR-0038 — The learning seam is declared and deliberately not implemented

- **Status:** **Accepted** — 2026-09-03 (declares a seam; implements nothing)
- **Phase:** 13
- **Affects:** `src/contexts/ai-intelligence` (port declaration only)

---

## Context

The obvious next capability is a system that learns from delivery history: which leading indicators
actually preceded margin loss, which interventions actually worked, how far project estimates are
systematically optimistic. The Phase 13 contract asks for the architectural seam and explicitly
forbids building it now (§5 C, §108).

The risk of building it now is not effort. It is that a plausible statistical output — *"73%
probability of RED within 60 days"* — is indistinguishable to a reader from a governed one, and this
product's entire value rests on that distinction being legible. Nothing in the POC is trained,
fitted, sampled or calibrated, and there is no held-out data to calibrate against, because the
history is synthetic and was generated by rules the model would then "discover".

## Decision

1. **Declare `HistoricalOutcomeLearningService` as a port with no implementation.** Its shape names
   the future capabilities — leading-indicator discovery, project similarity, calibrated outcome
   models, intervention effectiveness, estimation learning, threshold recommendation.
2. **The governance rule is stated on the port itself:** *governance defines policy; learning
   discovers patterns; learning may recommend policy changes; learning never silently modifies
   governance.* A discovered threshold is a proposal that becomes an ADR, or it is nothing.
3. **A future statistical output may not ship without all eight of:** train/validation separation,
   temporal holdout, calibration, drift monitoring, feature provenance, model version, explainability,
   and human governance sign-off. These are recorded as the acceptance gate now, before there is any
   pressure to ship without them.
4. **Until then, the product declines probability questions**, and the decline explains *why* rather
   than reporting a limitation. This is already implemented and tested.

## Rationale

Recording the acceptance gate before the capability exists is the only moment at which it can be set
honestly. Written afterwards, it is written by someone who already has a model they want to ship.

## Consequences

**Positive** — the seam exists, the shape is agreed, and the bar is set. **Negative** — the product
cannot answer the most commercially attractive question class, and says so every time.
