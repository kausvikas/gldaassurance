## 4. Deviations, declared

Per global invariant 4, documented as **ADR-0017 (Proposed)** *before* implementation and identified
explicitly here. Five changes, all to `architecture/manifest.json` or `tsconfig.json`; none touches a
formula, metric definition, domain boundary, security assumption, brand token, RAG logic or synthetic
scenario.

| # | Change | Why it was necessary | Direction |
| --- | --- | --- | --- |
| D-1 | `presentation.allowedExternal` → `["react","react-dom"]` | ADR-0001 §Decision 7 (Accepted) names React for presentation; the manifest still said `[]` from Phase 1, when no UI existed | **Alignment.** No new decision; the ADR already chose React |
| D-2 | G-COLOUR exempts `tokens/palette.ts` | `BRAND_DESIGN_SYSTEM.md` §3 requires the token layer to hold hex values; the gate forbade the only file that makes the rule satisfiable | **Neutral.** One declared exemption, asserted by test to remain exactly one |
| D-3 | G-DEMO activated over `src/presentation` | It was declared with `state: DEFERRED to Phase 6`. This is Phase 6 | **Strengthening** |
| D-4 | `lib` gains `DOM`; new **G-BROWSER** gate | `@types/react` needs DOM types, and there is one `tsc` project; the gate closes the hole that opens | **Net strengthening.** Nothing previously stopped a context calling `document.*` except that it would not type-check |
| D-5 | G-CLOCK and G-FLOAT extended to `src/presentation` | A component that reads the clock or parses a number has begun to compute — `PRODUCT_SPEC.md` §8 calls that a defect | **Strengthening** |

**One correction made during the phase, recorded because it is the kind that ships silently.** The
first draft of `BRAND_DESIGN_SYSTEM.md` §10 published four contrast ratios for the functional amber
and red that were wrong (7.05/6.35/10.19/9.98 against actual 6.33/5.70/9.68/10.15). All six values
still clear AA comfortably, so no colour changed — but the numbers were quotable and wrong. They are
now computed, corrected, and pinned by a test that also asserts the document publishes the same
figures.

## 6. Self-review

- [x] **Is any `IMPLEMENTED` claim resting on a UI that merely looks right?** No. Every assertion is
      on rendered markup or on recomputed arithmetic. The two claims that *would* rest on appearance
      — rendered contrast and keyboard traversal — are marked `PARTIAL` and carry DR-042.
- [x] **Does any component compute a business value?** No. Every figure is a pre-formatted string
      from the view model. The single exception is documented and bounded: `scale()` maps a supplied
      number to a pixel coordinate, and G-FLOAT now guards the boundary.
- [x] **Did any brand token, formula, threshold or scenario change?** No. `BRAND_DESIGN_SYSTEM.md`
      §1–§8 is untouched; the synthetic content hash is unchanged.
- [x] **Is authorization implemented or implied anywhere in the UI?** No. `requiresCapability` is a
      presentation hint, documented as such in three places, and a test asserts a hidden destination
      is still declared — the server decides, always.
- [x] **Is any mock unlabelled?** The gallery fixtures live in `scripts/design/fixtures.ts`, are
      labelled `DEMO — SYNTHETIC DATA`, and are not importable from `src/`.
- [x] **Could a Phase 7 screen be built without inventing a visual convention?** For the Portfolio
      Command Center, yes — KPI cards, ranked table, bubble triage, action cards, status conflict and
      evidence drawer are all present. The honest caveat is interaction, not appearance: DR-041.
- [x] **If a claim here is wrong, would we find out now or in front of the client?** Now, for tokens,
      contrast arithmetic, markup semantics and provenance. **In front of the client** for anything
      needing a browser — which is exactly why DR-042 exists and why §11 of the brand document lists
      it line by line rather than claiming WCAG conformance.
